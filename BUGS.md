# Bugs observed during rearrangement

- **FFmpeg recording resolution can disagree with the encoded frame size.** `begin_ffmpeg_recording` sets `m_snap_width`/`m_snap_height` to the configured `-aviwrite_scale` or `-aviwrite_res` dimensions when creating the writer, then restores the prior snapshot dimensions. Later, `record_frame` renders into an FFmpeg pool bitmap through `create_snapshot_bitmap(nullptr)` using those restored dimensions. The writer was created for the selected dimensions, but subsequent rendered frames can have different dimensions. Relevant changes: `e3117fa1d0320bd1dd6c657920276e0df3bef27e`; current paths: `src/emu/video.cpp` (`begin_ffmpeg_recording`, `record_frame`).
- **Temporary WASM diagnostics remain in normal emulator paths.** `src/emu/machine.cpp` writes several `DEBUG:` lines and flushes `error.log` during machine phases and every main-loop entry; `src/emu/video.cpp` appends a `FINAL SPEED REPORT` at exit and prints `WASM Speed` periodically. These diagnostics add file I/O and log output to ordinary execution. They originated in mixed commit `d5df6e745ce880cb29fecb326fecdb3e62dc8a18` and remain in the current tree.
- **UTF-8 conversion silently drops malformed input bytes.** In `src/lib/util/unicode.cpp`, `wstring_from_utf8` now advances one byte and continues when `uchar_from_utf8` reports invalid input, whereas the prior `wstring_convert` path reported conversion failure. This changes malformed-input behavior at every caller; assess whether replacement or explicit failure is intended. Introduced by mixed commit `d5df6e745ce880cb29fecb326fecdb3e62dc8a18`.
- **VVF statistics retain counters across recording instances.** `vvf_write::end_frame` uses function-static frame counters and color baselines, while `record()` resets the instance counters. A subsequent recording can subtract stale values (including unsigned underflow) and compare color counts against the previous recording. The static values were introduced in `1fa4352e5c2dad8124ff9febe18c03b0c35b87dc` and extended in `a7eb5ef439c817e69ea42bebe86349234e0533a1`; current code is in `src/osd/modules/render/vvfwrite.cpp` around `end_frame`.

- **Timed triggers share a timer across scheduler instances.** `device_scheduler::trigger` declares `static emu_timer *s_trigger_timer` inside the member function and initializes it with the first scheduler's `this`. A later scheduler instance reuses that timer, whose delegate still targets the first scheduler. The change is in `src/emu/schedule.cpp` and came from the split of mixed commit `d5df6e745ce880cb29fecb326fecdb3e62dc8a18`.
- **The 32-frame TPS window can never become valid.** `running_machine::emscripten_main_loop` stores timeslice timestamps in a 30-element array and caps `timeslice_timestamps_collected` at 30, but the 32-frame calculation requires at least 32 samples. Consequently `tps_32` remains zero and is used as the high-rate fallback in the stats log. Introduced by `7548279e227421c2280bc71b4a78c2d8190846e1`; current code is in `src/emu/machine.cpp` around the TPS sampling block.
- **The vector-frame-started flag is never reset at runtime.** `vector_device::clear_list` sets `m_vector_frame_started`; the only reset is inside a `#if 0` block in `video_manager::frame_update`, while `end_vector_frame` still uses the flag to gate work when `vector_frame_skip` is enabled. After the first vector frame, the flag can remain true and defeat that per-frame guard. The reset was disabled by current-lineage commit `cdbbe592d21dae8b75cc2cf7645d1ac660ea21c1` (equivalent phase25-checkpoint commit `649af5a08708eec6b64696148128cc93b2fea3df`); current paths are `src/emu/video.cpp` and `src/devices/video/vector.cpp`.
- **Dismissed browser performance warnings cannot reappear after an FPS drop.** The dismiss handler sets `isMonitoring = false`, but `monitorFrames` returns immediately while that flag is false. This prevents the later 5% drop check from running, despite the dismissal message promising another warning after such a drop. Current code is in `webdist/mame_performance_warning.js` around `monitorFrames` and the dismiss handler.
- **VVF line recording collapses vectors when either coordinate axis is constant.** `vvf_write::line_to` initializes both scaled coordinates to zero and performs scaling only when both raw X and raw Y ranges are nonzero (`if (!(m_min_raw_x == m_max_raw_x || m_min_raw_y == m_max_raw_y))`). A vertical or horizontal-only stream therefore encodes all points at `(0,0)` instead of preserving the varying axis. The guard is in `src/osd/modules/render/vvfwrite.cpp` around line 321 and was introduced by `f922611c5dce`.
- **VVF header comments still describe the old 2047 coordinate limit.** `vvfwrite.h` documents `vvf_width` and `vvf_height` as max coordinate 2047, but the current writer uses `BIT13_MAX = 8191` and offsets signed coordinates before writing 14-bit absolute values. This can mislead format readers; the stale comments date to `69cc93523935` and the 14-bit encoding is documented in `78fc010779fe`/`4cb78e7d46fe`.
